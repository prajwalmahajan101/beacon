# M3.2 journal — Multi-tenancy at the gateway layer

**Branch:** `feature/ingest-multi-tenancy` off `main@6059b5e`
**Goal:** Tenant isolation at the gateway: API-key auth, tenant stamping on Kafka records, per-tenant rate limiting, UUID attribute key rejection. Three INGEST requirements (02, 03, 15). One ADR-0027.
**Plan:** `.claude/plans/golden-forging-crayon.md` (5 waves, approved 2026-10-31).

## What I did

- **Wave 0 — GJF bump** (`b7613c9`): google-java-format 1.28.0 → 2.0.0 to fix Spotless on JDK 27. Mechanical reformat of 8 files. Pre-existing breakage, not M3.2-specific.

- **Wave 1 — API-key auth** (`9b9609e` RED, `4a6ca5d` GREEN): `GatewayProperties.Tenant` config model with `apiKey`, `tenantId`, `rateLimit` fields. `TenantResolver` builds `Map<apiKey, Tenant>` at startup. `ApiKeyAuthFilter` (HTTP `OncePerRequestFilter`) + `ApiKeyAuthInterceptor` (gRPC `ServerInterceptor`), both with open-mode pass-through when no tenants configured. Wired interceptor into `GrpcServerLifecycle`. 12 tests (5 unit + 4 HTTP IT + 3 gRPC IT).

- **Wave 2 — Tenant stamping** (`cc0e474` RED, `d361954` GREEN): Added `tenantId` field to `LogRecordProducer.KeyedRecord`. `IngestService.ingest(request, tenantId)` threads it through. `LogRecordProducer` builds `ProducerRecord` with `X-Scope-OrgID` Kafka header. HTTP controller extracts tenant from request attribute; gRPC service from `Context`. Vector config: `headers_key: "kafka_headers"` + remap extracts `.kafka_headers."X-Scope-OrgID"` → `.tenant_id`. 3 new IT tests verify header end-to-end.

- **Wave 3 — Rate limiting** (`fab64c0` RED, `c0b3248` GREEN): `TenantRateLimiter` with `ConcurrentHashMap<tenantId, Bucket>` token bucket. Clock-injectable (`LongSupplier`) for deterministic tests. `ApiKeyAuthFilter` → 429 + `Retry-After`. `ApiKeyAuthInterceptor` → `RESOURCE_EXHAUSTED`. Default 1000 rec/sec, per-key override. 5 unit tests + 2 ITs.

- **Wave 4 — Attribute key rejection** (`f22107c` RED, `f799c4b` GREEN): `IngestService.checkAttributeKeys()` with compiled `UUID_KEY` pattern. Records with UUID-shaped attribute keys rejected in `partial_success`. 2 unit tests.

- **Wave 5 — Docs** (this commit): ADR-0027, CHANGELOG, this journal, roadmap + requirements status updates.

## Problems I faced

- **Spotless/GJF JDK 27 breakage.** google-java-format 1.28.0 accessed a removed JDK internal field (`JCCompilationUnit.endPositions`). Fixed by bumping to GJF 2.0.0 (released 2026-10-30). Pre-existing issue, not introduced by M3.2.

- **Spring context sharing across auth ITs.** Rate limit tests needed a tenant with `rate-limit=1` to exhaust the bucket in 2 requests. Adding this tenant to the same `@DynamicPropertySource` as the auth tests risked interference. Solved by using a second tenant (`test-key-rl` / `tenant-rl` / rate-limit=1) alongside the main tenant (`test-key-1` / `tenant-a` / default 1000), so auth tests run on the high-limit tenant unaffected.

## What could have been done better

- The GJF version check could have been done proactively before starting M3.2, since the Spotless failure was pre-existing. It added an unplanned commit to the branch.
- Wave 2's Vector config change (`headers_key` + tenant_id remap) was not independently tested outside the Java ITs. A quick `docker compose` smoke test with a manual produce would have caught any VRL syntax errors early.

## Changes carried back to earlier phases

- `build.gradle.kts` (root, all milestones): bumped google-java-format 1.28.0 → 2.0.0 for JDK 27 compat. Mechanical reformat of SDK + spring-adapter test files.
- `deploy/vector/vector.yaml` (M3.0c/M3.1 artifact): added `headers_key: "kafka_headers"` to Kafka source and tenant_id extraction in `parse_json` remap.

## What's next

- **M3.3 (ES storage layout):** Index template (`flattened` attributes, `total_fields` cap), data streams, ILM with explicit delete phase, 10k-key stress test, p99 measurement. This is when M3.2's `tenant_id` field becomes load-bearing for query-time tenant isolation.
- **Carry-forward:** `TenantRateLimiter` is per-instance; cluster-wide rate limiting (shared Redis counter) deferred to M5. YAML tenant config doesn't scale past ~50 tenants; database-backed store deferred to M5.
