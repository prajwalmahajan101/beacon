## Problems I faced

- **Startup-race errors that self-heal.** On a fresh `up`, Vector's consumer subscribes to `beacon.logs` before the topic exists → one `UnknownTopicOrPartition` ERROR in the Vector log; the console producer's first metadata fetch likewise WARNs `UNKNOWN_TOPIC_OR_PARTITION`. Kafka auto-create then makes the topic, the record is produced, and Vector — because of `auto_offset_reset: earliest` — reads from the beginning once it (re)joins, so the record still lands in ES (hits=1). The errors are benign here but noisy; a cleaner smoke would pre-create the topic before producing. Recorded as an accepted skeleton trade-off (pre-create / DLQ is M3.1).
- **The timestamp-collision risk was real — and `log_namespace: true` is the clean fix.** In the legacy log namespace the Kafka source stamps top-level fields (including a `timestamp` from the Kafka message), which would collide with the M0 record's own `timestamp`. Turning on `log_namespace` routes all source metadata into the metadata namespace, leaving the decoded JSON as the event root. Confirmed by inspecting `_source`: exactly the 12 contract keys, no `%kafka` artifacts.

## What could have been done better

- I could have pre-created `beacon.logs` in the smoke script (a one-line `kafka-topics.sh --create`) to silence the transient startup errors and make the log cleaner for a first-time reader. Left it out to keep the script minimal and to exercise the same auto-create path the gateway relies on — but it's the obvious polish if the noise ever confuses a debugging session.
- `vector validate` needs `--no-environment` to pass without live upstreams; I found that by running it, not by reading the docs first. Minor.

## What's next

- **Hand-off to M3.0d (5.3):** the smoke script is deliberately CI-shaped (non-zero on failure, `SMOKE_KEEP`) — 5.3 can either wire it into the new `.github/workflows/ingest.yml` gate or supersede it with the full Testcontainers E2E that emits via the real Java + Python SDKs through the gateway (this slice seeds Kafka directly and does not exercise the gateway). The gateway→Kafka→Vector→ES path is now complete end-to-end for a hand-seeded record.
- **v2 / carry-list:**
  - ES dynamic-mapped `timestamp`/`observed_timestamp` as `date` and accepted the RFC3339-ns string, but stores it at **ms precision** (sub-ms truncated). Nanos-preserving mapping (or storing epoch-nanos) is **M3.3** (index template + `flattened` attributes + ILM).
  - At-least-once + auto `_id` ⇒ a Kafka redelivery double-indexes. Dedup via the composite `(service.name, hash(trace_id)%N)` key + offset-commit-after-write is **M3.1**.
  - Pre-create the topic (or accept auto-create) — decide alongside the DLQ/partition-key work in **M3.1**.
  - Per-item bulk status is only logged on the **failure** path (Vector is silent on successful items at `info`); if richer indexing observability is wanted, revisit when self-observability lands (M5.1).
