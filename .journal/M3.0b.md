# M3.0b journal — Ingest gateway (OTLP-in / M0-JSON-out)

**Branch:** `feature/ingest-gateway` off `main@fad3397`
**Goal:** the thin Spring Boot OTLP gateway that fills the ADR-0024 compose seam — accept OTLP (gRPC 4317 + HTTP 4318), reconstruct + validate the M0 record, produce canonical JSON to Kafka with response-after-ack. Reqs INGEST-01, INGEST-04.
**Plan:** `.code_assist/.plan/m3.0b-ingest-gateway.md` (T1–T12).

## What I did

- **T1 — scaffold.** New top-level `platform/gateway` (`:beacon-gateway`), Spring Boot 3.3.5 + dependency-management plugins. Catalog pins: `opentelemetry-proto 1.10.0-alpha` (protobuf-java 4.34.0 runtime) + `grpc-bom 1.82.1` (grpc-netty-shaded/stub/protobuf). Resolved the exact otel-proto/grpc versions from Maven Central metadata before writing the build, and confirmed the jar ships both the OTLP messages and the `LogsServiceGrpc` stubs.
- **T2 — config.** `GatewayProperties` (`beacon.gateway.*`) for grpc-port + topic + produce-timeout; `application.yaml` puts the idempotent `acks=all` producer under `spring.kafka.*`, OTLP/HTTP on 4318, actuator on a separate management port 9464.
- **T3 — schema + validator.** `processResources` build-time-copies the frozen `contract/schema/log-record.schema.json` into the jar; `RecordValidator` (com.networknt Draft 2020-12) returns ordered reasons. Test drives the contract's own valid + all 8 invalid example fixtures.
- **T4 — mapper.** `OtlpRecordMapper` reconstructs the M0 `LogRecord` from OTLP, reusing the SDK's `LogRecord`/`CanonicalJson`/`SeverityMapper`; injects `schema_version=1`; body coercion, observed-time fallback, hex ids (all-zero dropped), severity-text derivation.
- **T5–T6 — producer + orchestration.** `LogRecordProducer` (sync `acks=all`, pipelined sends awaited to timeout); `IngestService` runs map→validate→produce, tallying rejects into `IngestResult` (`partial_success`) vs `kafkaFailed` (5xx).
- **T7–T8 — transports.** `OtlpHttpController` (`POST /v1/logs`) + `OtlpGrpcLogsService` on a standalone grpc-netty-shaded `Server` (`GrpcServerLifecycle` `SmartLifecycle`), both delegating to `IngestService`.
- **T9 — observability.** Micrometer `ingest.accepted|rejected|kafka_failure`, `CorrelationIdFilter`, actuator `/health`.
- **T10 — container + compose.** Multi-stage Dockerfile (repo-root context, bootJar → JRE, non-root, curl for the healthcheck); the commented compose seam became a real `gateway:` service; `BEACON_ES` dropped. Full stack `up -d --wait` healthy; POST → canonical record on `beacon.logs`; `down -v` clean.
- **T11–T12 — ADR-0025 + closure** (this entry, CHANGELOG, requirement ticks, roadmap flip). 12 atomic commits.

## Problems I faced

- **The Testcontainers / docker-java toolchain fight (T5, the big one).** The producer IT couldn't reach Docker: first `Could not find a valid Docker environment`, which I initially misread as the harness sandbox blocking the socket. It wasn't — the real error under the summary was `client version 1.32 is too old. Minimum supported API version is 1.40`. docker-java uses `1.32` as its URL prefix whenever `apiVersion` is *unset*, and Docker Engine 29 rejects it. The rabbit hole had three layers: (1) the native `apache/kafka` KRaft container class only exists in Testcontainers ≥ 1.20, but the Boot BOM manages 1.19.8 → bumped to 1.21.4; (2) the Boot BOM *also* forces docker-java 3.3.6, older than the 3.4.2 TC 1.21.4 targets → pinned docker-java 3.4.2 with explicit test deps (which beat spring-dependency-management); (3) the decisive one — docker-java reads the pinned version from the **`api.version` system property**, NOT the `DOCKER_API_VERSION` env var I kept setting. I only found it after a diagnostic test confirmed the env var *was* reaching the fork yet 1.32 persisted. `systemProperty("api.version", "1.41")` on the test task fixed it instantly. Also: the persistent Gradle daemon caches its start-time env, so every retry needed `--stop` first.
- **`CanonicalJson` NPEs on null (T4 design).** The SDK's serializer dereferences `timestamp().toString()` and `writeString(body)` with no null guard (the SDK's emit path never passes null). For the gateway, a genuinely-missing OTLP timestamp/body would NPE the whole request instead of rejecting that one record. Rather than modify shared SDK code, I made the mapper throw `RecordMappingException` for the two un-serializable fields, funneling them into the same reject tally the validator feeds. Every *other* invalidity (severity, resource attrs, id patterns) maps fine and is caught by the schema validator — clean split.
- **Empty OTLP response = null body (T7).** A fully-accepted `ExportLogsServiceResponse` is an empty proto (0 bytes), which `TestRestTemplate` surfaces as `getBody() == null` → `parseFrom(null)` NPE. Guarded with `bodyOrEmpty`.
- **Suite-wide flakiness, only when run together (T12).** Class-by-class the ITs were green; `:beacon-gateway:test` as a whole failed three. Two causes: the `@Container` static broker is shared across all `KafkaContainerSupport` subclasses via inheritance and gets stopped by the first class's `afterAll`, so later valid-produce ITs hit a dead broker → switched to the singleton-container pattern (start once in a static initializer, Ryuk reaps at exit). And the context-load test asserted `grpc-port==4317`, stale after the module-wide test `application.properties` override to 0.
- **Fixed ports across cached contexts.** Every `@SpringBootTest` starts the gRPC lifecycle; multiple cached contexts on the fixed 4317 (and management 9464) clash. Fixed with a module-wide test `application.properties` binding both to `0`.

## What could have been done better

- I burned real time treating the Docker failure as a sandbox problem before reading the *actual* strategy log line. Lesson: when Testcontainers says "no valid environment," always pull the per-strategy exception first — the summary hides the real cause.
- I should have anticipated the shared-static-container lifecycle trap when I first wrote `KafkaContainerSupport` (it's a known Testcontainers footgun with inheritance); instead I discovered it only in the final all-together run. Writing the singleton pattern from the start would have saved a debugging loop.
- The per-record reject-on-missing-timestamp/body logic in the mapper is slightly subtle (two layers of "invalid"); a short comment block earns its keep there, which I added.

## Changes carried back to earlier phases

- None to shipped code. The only cross-cutting change was **test-scope dependency overrides** in `gradle/libs.versions.toml` (Testcontainers 1.21.4, docker-java 3.4.2) — additive, test-only, no effect on the SDK or contract modules. `CanonicalJson`/`SeverityMapper`/`LogRecord` were reused **unmodified** (a deliberate constraint — the gateway adapts around them rather than editing frozen-adjacent SDK code).
