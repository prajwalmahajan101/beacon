## Problems I faced

- **Testcontainers `ComposeContainer` rejects `container_name` — at parse time.** My plan assumed local-compose mode would run the file verbatim (it does for *execution*), but TC *validates* the compose file in the constructor and hard-fails on `container_name` before `withLocalCompose` is ever consulted. Removed `container_name` from both files (functionally inert — service names + `localhost` carry all real wiring). Recorded as a deviation.
- **The gateway image was rebuilt every run — flakily.** TC uses a random compose project name per run, so a pre-built image can't be reused; `up --build` re-ran the in-Docker Gradle `bootJar`, which hit a transient TLS/SSL failure downloading dependencies. Fix: stable `image: beacon-gateway:local` tag + `withBuild(false)`, with `ingest.yml` pre-building once.
- **The nastiest one — OTel version skew, a latent SDK gap.** The first Java run (direct) died with `NoClassDefFoundError: io/opentelemetry/api/incubator/logs/AnyValue`, and the collector run silently found nothing (Pitfall #29: the OTLP `force_flush` swallowed the failure, so it looked like a plain miss). Root cause: the E2E is the FIRST place the SDK's real `OtlpExporter.accept()` runs — the SDK's own tests never exercise it — and on the **gateway** module (Spring Boot dependency management) `exporter-otlp`/`sdk-logs` were downgraded to Boot's managed **1.37.0** while `opentelemetry-api-incubator` (where `AnyValue` lives) floated **up to 1.44.1-alpha** via the logback-appender. An `enforcedPlatform(opentelemetry-bom)` did NOT fix it — the Spring DM plugin overrode the platform constraint. What worked was `resolutionStrategy.eachDependency` (which *does* beat Spring DM), realigning the whole `io.opentelemetry` surface to the SDK's compiled **1.42.0** on the test classpaths only. Both tests went green immediately after. **Later root-fixed in-branch** (see "Changes carried back"): a strict `opentelemetry-api-incubator` constraint in `sdk/java/core` (Problem A, all consumers) + an OTel BOM import via Spring `dependencyManagement` in the gateway (Problem B, Spring-DM downgrade), and the `eachDependency` workaround was deleted — the E2E stays green without it.

## What could have been done better

- I planned "Testcontainers wrapping the real compose file, local-compose mode" without checking that TC validates-and-rejects `container_name` up front — a five-minute check of `ParsedDockerComposeFile` would have surfaced the `container_name` + image-name + build-flakiness cluster before execution and folded them into the plan instead of as three mid-flight deviations.
- The OTel skew is really an **SDK bug** (its real exporter can `NoClassDefFoundError` under Spring dependency management). I scoped the fix to the E2E test classpath to keep M3.0d tight, but the right long-term fix is in the SDK/Spring adapter (pin/expose the incubator). Logged in "What's next".

## Changes carried back to earlier phases

- `docker-compose.yml` (M3.0a/M3.0b/M3.0c artifact): removed `container_name` from all services and added `image: beacon-gateway:local` to the gateway. No behavioural change — service DNS names, healthchecks, the M3.0c smoke script (`docker compose exec <service>`) and inter-service wiring are unaffected; only `docker ps` labels change to `beacon-<svc>-1`.
- **SDK OTel-consistency fix (root-caused from the E2E):** `sdk/java/core` now carries a strict `opentelemetry-api-incubator` constraint pinning it to the SDK's OTel line, so the incubator can't float off `sdk-logs`/`exporter-otlp` and `NoClassDefFoundError` the real exporter for *any* consumer (core, `beacon-sdk-spring-adapter`, gateway). The gateway additionally imports the OTel BOM via Spring `dependencyManagement` to stop Boot's BOM downgrading the stable artifacts. This replaced the initial test-classpath-only `eachDependency` workaround; no gateway/SDK *runtime* code changed.
