## Problems I faced

- **The atexit-vs-SIGTERM convergence (the load-bearing decision).** Python's exit model splits across two paths that do NOT natively converge — unlike Java's single JVM shutdown hook (ADR-0006). `atexit` runs on normal exit but NOT on a raw SIGTERM (the default disposition kills the process, skipping every hook → all pending records lost on a container stop). And a SIGTERM handler that drains then exits normally ALSO triggers `atexit`, firing the drain a second time. Resolved by routing BOTH paths through the SAME `beacon_shutdown()` guarded by a `threading.Lock` + `_shutdown_done` bool (ADR-0017 #4): the second fire is a guarded no-op, so the drain runs exactly once regardless of ordering. This is Pitfall #26 and the single most important call of the phase.
- **Which SIGTERM→exit convergence mechanism.** Three candidates: (a) chain to the previous SIGTERM handler, (b) restore `SIG_DFL` and re-raise, (c) `raise SystemExit(0)` after draining. Chose (c). (a) is brittle — the previous handler may `os._exit` (skipping our drain) or not exist. (b) kills the process before `atexit` runs, losing the normal-exit drain path AND the clean returncode. Only (c) converts SIGTERM into a *normal* exit, which is what makes `atexit` fire at all (so a raw SIGTERM no longer skips the drain) AND lets the container stop cleanly (returncode 0, not `-SIGTERM`) — the subprocess test's `returncode == 0` assertion is exactly this convergence proven cross-process.
- **The no-import-side-effects invariant.** Importing a library must not silently mutate the process's `atexit` table or signal disposition — surprising and un-composable. So registration is LAZY: `ensure_shutdown_registered()` (the seam the future `emit()` + `build_pipeline` call) installs the hooks on FIRST use, never at import. Tested in-process (`test_import_has_no_side_effects` — the SIGTERM handler is unchanged and `_atexit_registered` is False after a reset), and cross-process by the subprocess test (a fresh interpreter that only arms the handler after `build_pipeline`).
- **`signal.signal` off the main thread raises `ValueError`.** CPython only allows signal-handler installation from the main thread. `ensure_shutdown_registered` guards with `threading.current_thread() is threading.main_thread()` and a `try/except ValueError` — off the main thread the SIGTERM install is skipped entirely (atexit-only path remains; a daemon/worker-thread host owns signals). `test_ensure_registered_skips_sigterm_off_main_thread` runs inside a `threading.Thread` and asserts the handler is unchanged with no `ValueError` propagated.
- **The subprocess "ready" race.** The parent must not send SIGTERM before the child has armed its handler AND buffered its records — otherwise it tests nothing. The child prints `READY` (flushed) ONLY after `build_pipeline` (which arms the handler) + buffering, then blocks on `signal.pause()`; the parent reads that line (failing with the child's stderr if it never arms) before `os.kill`. That handshake closes the race deterministically.
- **The `endpoint=None` fallback path is non-deterministic in CI (Plan 03, Rule 1 deviation).** The plan's primary suggestion was to build the subprocess child with `ExporterConfig(endpoint=None, fallback_sink="file:<path>")` and rely on the no-endpoint `OtlpExporter` fail-fast raising into the `ResilientSink` fallback. Live, the OTel gRPC exporter resolves the default `localhost:4317`, does its OWN internal retry/backoff on `UNAVAILABLE` (`retrying in 1.03s`), and `force_flush(5000)` returns without our `OtlpExportError` being raised — so `records_exported=0/export_failures=0/fallback_writes=0` and NOTHING reached the file (exactly the "status hidden behind a bool" concern M2.3/ADR-0016 §6 flagged). Switched the child to the `build_pipeline(..., sink=)` test-override seam (which the plan explicitly authorized) with a deterministic `_AlwaysFailDelegate → FileFallbackSink`, so every exhausted batch lands in the file exactly once.

## What could have been done better

- **Whether emit-after-shutdown should have been gated now.** ADR-0017 #6 defers it (parity with ADR-0006 #6), and it is doubly moot since there is no top-level `emit()` until M2.6. But that means for one milestone the tree has a `beacon_shutdown()` that drains and a (future) emit path that could still push to a drained buffer with no consumer. It is the right call — gating every future entry point is non-trivial and premature — but "drained but not gated" is a shape a future reader should not mistake for an oversight, hence it is documented in the ADR Consequences.
- **The subprocess test's returncode assertion is tight by design but could mask a partial drain.** Asserting `returncode == 0` proves the clean `SystemExit(0)` convergence, and the `≥ 200 JSON lines` check proves the drain actually moved records — together they are strong. But a future contributor tuning the timeout could get a child that exits 0 having drained *fewer* than 200 if the drain window were too small; the `≥ 200` line-count is what actually guards that, and it is worth keeping both assertions rather than trusting returncode alone.
- **`build_pipeline` lives in `lifecycle/_shutdown.py`.** Co-locating the assembler with the shutdown registry keeps the module-registry access private and dodges a circular import, and the plan allowed a sibling `_pipeline.py` "if cleaner." It is fine for now, but once a genuine top-level SDK assembler exists (M2.6-era), `build_pipeline` arguably belongs there, not in `lifecycle/` — flagged so the eventual move is a deliberate refactor, not a surprise.

Same gate-then-drain-outside-the-monitor shape Java uses. The C9-in-miniature unit test (200 pending, huge size+interval so only the drain empties the buffer) previewed exactly the C9 shape Plan 03 would land.

Writing `beacon_shutdown(*args)` first, then `_sigterm_handler`, then `ensure_shutdown_registered` made the convergence story fall out naturally: one guarded function, two call sites (atexit + signal), `*args` bridging the two call shapes. The SystemExit(0) choice took the most thought — I wrote out all three mechanisms in the ADR before committing, because getting it wrong means either a raw SIGTERM skips the drain (SIG_DFL re-raise) or a fragile dependency on someone else's handler (chaining). `build_pipeline` retiring the `NOOP` seam was satisfying — the M2.2 ADR literally named this the M2.4 seam and here it closed. Lazy registration + the main-thread guard were the two invariants I most wanted tested in-process before trusting the cross-process test.

The child exiting returncode 0 (not `-SIGTERM`) is the cross-process proof of the SystemExit(0) convergence — the single most satisfying assertion of the phase.
