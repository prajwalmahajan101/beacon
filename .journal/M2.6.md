## What I did

- **Emit facade + handler (Plan 01).** `beacon.pipeline.EmitPipeline` composes the existing conformance-green stages (`Enricher` / `Redactor` / `BoundedBuffer`) into one non-blocking `emit(record)` — reimplements nothing. On `RedactorTimeoutError` it routes the ORIGINAL record to the fallback and returns `False` (never partial PII, never a silent drop). `build_emit_pipeline` constructs ONE `BoundedBuffer` and threads it through the M2.4 `build_pipeline(buffer=...)` so the facade offers into and the flusher drains from the SAME buffer — the shared-buffer handoff. `BeaconLoggingHandler(logging.Handler)` maps stdlib → beacon, captures `time.time_ns()` at handle time (PSDK-03), and wraps its whole body so it NEVER raises into the host logger. Zero-arg `BeaconLoggingHandler()` lazily builds a module-default on first emit.
- **Framework-free sample (Plan 02).** `examples/python-sample/` — a plain synchronous stdlib-`logging` script (no web framework, locked decision #5). Because the zero-arg default isn't observable collector-free (the OTLP swallow, below), the demo wraps an always-raising delegate in the SDK's own `ResilientSink` with a `file:` fallback and passes it via `build_emit_pipeline(sink=...)`, so 3 real canonical-JSON records land in `beacon-sample.log` via the SAME `ResilientSink → FileFallbackSink` path production uses. README documents the one-liner headline + the `beacon.context` propagation pattern.
- **Overhead benchmark + CI (Plan 03).** `benchmarks/emit_overhead.py` — a dependency-free stdlib `perf_counter_ns` benchmark of the real `EmitPipeline.emit` hot path (empty redact set = the Java floor), published to `docs/benchmarks/python-sdk-overhead.md`. Measured p99 ≈ 30 663 ns, ~33× under the 1 ms NFR-6 budget. CI now runs the sample as an integration smoke test + uploads the pytest-HTML artifact.
- **Phase-close (Plan 04, this one).** ADR-0020 + CLAUDE.md index (0001–0020) + M2-ROADMAP cross-links; CHANGELOG `[Unreleased]` M2.6 block; this journal; Pitfall #28 + #29; REQUIREMENTS PSDK-06/09 → Satisfied, PSDK-01/02 re-affirmed; PR opened against `main` (human ship checkpoint — no rebase-merge).

## Problems I faced

- **The OTLP `force_flush` swallow (the load-bearing finding).** The default `OtlpExporter` path's `force_flush()` returns `True` on connection-refused — OTel-Python's gRPC/HTTP exporter reports export *success* even when the collector is down. So `OtlpExporter.export` never raises `OtlpExportError`, `ResilientSink` never sees a failure, its retry-then-fallback branch never engages, and records against a dead/absent collector are silently counted as exported and LOST. This surfaced live in Plan 01 (the lazy-build test leaked a flusher thread stuck in the exporter's own retry loop) and again in Plan 02 (the pure zero-arg one-liner emitted nothing observable collector-free). C6/C7/C8 conformance passed only because they inject RAISING fake `BatchSink`s, not the real `OtlpExporter` — they never exercised this real-exporter swallow. **Decision (user-approved at the Wave 2 checkpoint): track as a follow-up, do NOT fix SDK source in M2.6.** Recorded honestly as Pitfall #29 (a TRACKED SDK defect for a dedicated future phase), a Technical-Debt-Patterns row, the ADR-0020 carry-list, this journal, the CHANGELOG known-limitation note, and the sample README.
- **The shared-buffer split.** The first instinct was to let `build_pipeline` construct its own buffer while the facade offered into a separate one — which would silently lose every emitted record (the facade fills buffer A, the flusher drains buffer B). The fix was the keyword-only `build_pipeline(buffer=...)` seam and a shared-buffer integration test proving an emitted record reaches an injected capturing sink after `drain_and_stop`.
- **Benchmark honesty.** A single-workload emit-path microbenchmark with the GIL held and no collector is a *floor*, not a production number. Framed it as such (CPython's interpreted hot path is ~30× costlier per op than JIT Java's 363 ns p50; still 33× under budget) with the GIL/jitter, no-GC-modeling, empty-redact-set, and CPython-only carve-outs named (Pitfall #28).

## What could have been done better

- The OTLP swallow could have been caught in M2.3 (the exporter phase) rather than M2.6 (the first real end-to-end emit). A collector-down integration test against the real `OtlpExporter` — not just injected fake sinks — would have surfaced it two phases earlier. The conformance suite's use of raising fakes is correct for isolating the `ResilientSink` contract, but it left the real-exporter connectivity behaviour untested; the deferred fix should add exactly that test.
- The stdlib float-`created` timestamp fidelity limit is a documented sub-microsecond gap — acceptable, but a future async handler variant would widen it, so the tradeoff is worth revisiting if an async handler is ever added.

## Changes carried back to earlier phases

- **`build_pipeline` (M2.4) gained a keyword-only `buffer=` parameter.** A plain function param (None default) — NOT a new `BEACON_*` key — that preserves the exact M2.4 internal-construction behaviour when omitted (all 8 lifecycle tests stay green) and threads the shared buffer when supplied. This retired the last M2.6-deferred emit-path wiring: `build_emit_pipeline` is the first production caller of `ensure_shutdown_registered()`.
- No M2.0–M2.5 behaviour changed otherwise; the emit facade composes the existing stages, and the M0-frozen conformance harness stayed untouched (`grep -c 'def test_c[0-9]'` stays 13; drift exit 0).

## What's next

- **The tracked OTLP fallback-swallow defect (Pitfall #29) — a dedicated future phase.** Teach `OtlpExporter` to detect a dead/absent collector (probe the channel state / inspect the per-batch result rather than trusting `force_flush`'s boolean, or add a connectivity pre-check) and raise `OtlpExportError` so `ResilientSink` engages retry→fallback as designed. Add a collector-down integration test against the REAL exporter. Until then the zero-arg one-liner is honest only with a live collector present.
- **M2.7** — the `v0.3-m2` release cut (PSDK-10): `CHANGELOG [v0.3-m2]`, `docs/M2-COMPLETE.md` retrospective, git tag `v0.3-m2`.
- A framework starter (FastAPI/Django/Flask request-scoped enrichment) remains an ADR-gated carve-out if adoption demands it — the stdlib handler subsumes the need for now.

## Journal

- The most important decision this phase was NOT a code decision — it was choosing to track the OTLP swallow as a defect rather than paper over it. The zero-arg one-liner is the headline of the whole Python SDK story; a lesser instinct would have quietly shipped it and let the first user discover the silent drop. Documenting it in five places (Pitfall, tech-debt table, ADR carry-list, CHANGELOG, sample README) is the learning-in-public tax, paid honestly.
- The framework-agnostic choice (no starter) reads as "less work" but is actually the more defensible design: Java needed a Spring starter because it has no universal logging facade wired into every framework; Python's stdlib `logging` IS that facade, and `contextvars` copy-on-spawn removes the `TaskDecorator` that made Java's starter necessary. ADR-0020 records that this is a real architectural asymmetry, not a shortcut.
- The p99 ≈ 30 663 ns result is the kind of number that's only meaningful with its caveats attached. Reported bare it invites "Python is 30× slower than Java"; reported with the floor/JIT/GIL framing it's "the interpreted caller-thread path clears the shared 1 ms budget with 33× headroom" — the same claim, honestly scoped.
