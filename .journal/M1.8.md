## Problems I faced

- **The kebab→camel mapping for the composite `redact` surfaces is
  bespoke and easy to get wrong.** YAML carries `redact.keys` /
  `redact.defaults` / `redact.timeout-ms`; `BeaconConfig` carries
  `redactKeys` / `redactDefaults` / `redactorTimeoutMs` (note the third
  is *not* `redactTimeoutMs` — the M1.6 record predates ADR-0009 §3's
  composite fold, so the internal field still carries the legacy
  spelling). Two places now hardcode this mapping: Java's
  `ConfigKeysContractTest.COMPOSITE_CHILD_TO_COMPONENT` and the Python
  drift checker's equivalent table. M2's Python SDK will need a third
  encoding. Three copies of the same table is a smell — a successor ADR
  may consolidate it into the YAML itself (e.g. an explicit
  `internal_field:` row alongside `name:`), but for M1.8 the trade-off
  was acceptable.

- **`samplingRatio` is a `BeaconConfig` record component but has no
  env/sysprop wiring in `BeaconConfigLoader` today.** Plan 03-01
  surfaced this and took the Path A route: added the
  `BEACON_SAMPLING_RATIO` + `beacon.sampling-ratio` `static final String`
  constants (so the contract test passes), but did not add the
  `resolveSamplingRatio()` method or `applyOverrides` extension. The
  contract test is loose enough — "literal string must appear anywhere
  under `src/main`" — that the reserved constants are sufficient. M2
  inherits the wiring work as part of Python parity. Whichever SDK adds
  the resolution path first should mirror it on the other side.

- **The `SeverityMapper` refactor required mutating enum instance
  fields at static init.** Keeping the public API stable (`numberFor` /
  `textFor` / `bandFor`) while moving the band table out of the inline
  enum constructor and onto the contract artifact meant the loader had
  to populate the `Band` instances *after* they construct. Unusual
  pattern; documented in the `SeverityMapper` Javadoc. Worse, accessing
  `Band.INFO.anchor()` from another class (e.g. `BeaconLogbackAppender`'s
  switch default) does *not* trigger `SeverityMapper`'s static init per
  JLS 12.4.1 — it triggers `SeverityMapper$Band`'s only. So `Band`'s
  static init now trampolines into
  `Class.forName(SeverityMapper.class.getName())` to force the enclosing
  class's init (and thus the loader) to run. The recursive class-init
  lock (JLS 12.4.2) keeps the back-edge safe. Symptom that drove the
  fix: `LogbackAppenderTest.appendsInfoEventToCapturingSink` failing with
  `severityNumber expected: 9, but was: 0`.

- **The drift-checker regex parsing of Java records is brittle.** An
  IDE-driven refactor that wraps a long record-header line, or adds a
  comment between the record name and its parameter list, could break
  the parser. Caught only by CI red. Mitigation today: a `printf`-style
  pre-flight in the script that asserts the record header matches before
  attempting to extract components. Real fix is M2: have Gradle emit a
  JSON of effective surfaces and have the Python checker read that
  (open question logged in Plan 03-03 SUMMARY).

- **The OTel SDK version review (Plan 03-04) was deliberately
  conservative.** Latest stable is 1.63.0 (21 minor versions ahead of
  our 1.42.0 pin); instrumentation BOM latest is 2.29.0-alpha (19 minor
  versions ahead). The bump touches `OtlpExporter`'s hand-translation
  from Beacon `LogRecord` to OTel log records (timestamp ns, severity
  band, attribute flattening) and `BeaconLogbackAppender`'s extension of
  the alpha-track instrumentation appender contract. That cross-cut
  doesn't fit the M1.8 release-cut window — it's M2 work, coordinated
  with Python parity. Path B (DEFER) recorded in ADR-0011 §Decision 3.

- **The `CanonicalJson` NPE root cause hunt.** The M1.7 benchmark
  surfaced an NPE in `writeMap` via the warmup-iteration `FallbackSink`
  path; the M1.7 known-issue note hypothesized "likely `resource` or
  `severityAttributes`." `severityAttributes` doesn't exist in the
  `LogRecord` record (the 12 components are
  schemaVersion/timestamp/observedTimestamp/severityNumber/severityText/body/traceId/spanId/traceFlags/resource/scope/attributes),
  so the hypothesis was half-wrong. Confirmed at M1.8: the floor
  workload sets `attributes` non-null but leaves `resource` and `scope`
  null; both flow into `writeMap(sb, null).entrySet()` on the
  FallbackSink path. Live `BatchSink` callers never invoked
  `CanonicalJson.serialize`, which is why C1–C12 stayed green and only
  the benchmark surfaced it. Fixed with a single defensive guard at
  method entry; 4-test regression pins each path (null map, empty map,
  nested null value, full `LogRecord` with all three nullable map
  components null).

## What could have been done better

- **The drift checker could be JVM-based.** Source-level regex was
  chosen because `contract.yml` runners have no JDK; today the checker
  would have to either pull a JDK into `contract.yml` (large CI
  footprint) or duplicate the checker per workflow. Open for M2 to
  revisit — have `./gradlew :beacon-sdk-java:printContractSurfaces`
  emit a deterministic JSON list of `(recordComponentName, envSpelling,
  syspropSpelling)` and have a smaller Python script diff that against
  the YAML. Less fragile than regex.

- **The contract artifacts could have a meta-schema.** A JSON Schema
  describing `config-keys.yaml` and `severity-table.json` themselves
  would be belt-and-braces over the contract tests + drift checker.
  Deferred (ADR-0010 §5) until M2 surfaces a drift class the regex
  checker misses.

- **The composite-redact encoding in YAML (parent `redact` + 3
  `nested_of: redact` children with their own env/sysprop spellings) is
  non-obvious.** A more conventional shape (nested map under `redact`)
  would have been easier for M2's loader. Trade-off was
  order-preservation + flat iteration on the Java side. Revisit if M2
  finds friction.

- **Still no Log4j2 sibling appender.** Slipped from M1.7 (per the
  M1.7 journal) and slipped again here. M1.7 + M1.8 both scoped tight
  to release-critical work; Log4j2 is "nice to have" until a real user
  asks for it. Carry to M2 (or M3 if M2 needs the bandwidth).

## Journal

13 vs 15 was the headline arithmetic of the milestone. `BeaconConfig`
has 15 record components, ADR-0009 §3 said 13 canonical *surfaces*, and
the kebab→camel mapping for the composite `redact` was the bridge — but
it took writing it out in `ConfigKeysContractTest.COMPOSITE_CHILD_TO_COMPONENT`
to be sure I had it right. The warmup-iteration NPE hunt was the same
shape: M1.7's note said "likely resource or severityAttributes," and
`severityAttributes` turned out not to exist in the record at all — the
half-wrong hypothesis would have wasted real time if I'd grepped for it
first instead of just reading the `LogRecord` definition. The OTel
version-review deliberation was the most interesting decision of the
phase — there is no good answer to "do we bump 21 minor versions in
the release-cut window or defer to the next milestone?", just a less-bad
one. The defer landed in ADR-0011 with a clear M2 carry; the bump-or-justify
cadence is now policy, not folklore. The class-init trampoline in
`SeverityMapper.Band` was the surprise — JLS 12.4.1 is one of those
specifications that you re-read every couple of years and discover a
new corner. The recursive class-init lock at 12.4.2 makes the back-edge
safe; without it, the trampoline would deadlock the first thread that
touched `Band.INFO`. Small thing. Worth a Javadoc paragraph.
