# M1.6 — Redactor + MDC/Context enricher + async-context propagation → 12/12 conformance

**Note:** written live as the phase shipped (2026-06-20), not backfilled.

**Branch:** `feature/m1-6-redactor-mdc-context-enricher` off `main@6d1e908`
**Goal:** un-disable conformance C10 (redaction) + C11 (trace context, sync + async) — last two of 12 — and lock the M1.6 emit pipeline (`enricher → redactor → buffer`) plus the disk-floor route for unredacted records.
**Plan files:** `.planning/phases/01-m1-6-redactor-mdc-context-enricher/01-{01..04}-PLAN.md`

## What I did

Four atomic plans, mirroring the M1.0–M1.5 cadence:

1. **01-01 — config + loader** (`feat(01-01)` x2 + `test(01-01)`): `BeaconConfig` 14th key `redactorTimeoutMs` + `redactDefaults` behavior flag, `BeaconConfigLoader` with env > sysprop > builder precedence, `LogRecord.Builder.from(LogRecord)` copy helper, slf4j-api 2.0.16 on the SDK runtime classpath. Phase-3 todo dropped at `.planning/todos/cont-01-14-keys.md`.
2. **01-02 — redactor** (`feat(01-02)` x2 + `test(01-02)` + `docs(01-02)`): `Redactor` iterative literal-key walker with `System.nanoTime()` deadline, depth cap 32, length-based short-circuit on `matches()`, `RedactorTimeoutException` carrying the original record, `SdkMetrics.redactorTimeouts` (9th counter). ADR-0007 locks every redaction decision.
3. **01-03 — enricher** (`feat(01-03)` + `test(01-03)`): production `Enricher` with OTel-`Span.current()` > MDC fallback, W3C hex-shape validation, read-only on OTel Context (never `spanBuilder`), logback-classic 1.5.12 as `testRuntimeOnly` so SLF4J actually has an MDCAdapter.
4. **01-04 — executors + conformance** (this plan; 5 atomic commits): `BeaconExecutors` (the four `wrap(...)` factories), `BeaconSdk.emit` pipeline wiring + dedicated `redactorFallbackSink` field, `BeaconLeakGuard` JUnit extension, C10 + C11 un-disabled with the four C11 sub-cases (sync OTel, sync MDC, async `CompletableFuture`, async Spring `@Async`), C2 leak fix (try/finally + `sdk.close()`), spring-context 6.1.14 + logback-classic on `:conformance-java`'s test classpath, ADR-0008.

Conformance harness now **12/12 green** on Java (C1..C12). The flusher-daemon leak the project had been carrying since M1.3 (C2) is gone.

## Problems I faced

- **`LogRecord.body` is typed `String`, not `Map`.** CONTEXT.md's "scan body if Map" turned moot. Resolved by ADR-0007 deferring body-string scrubbing to v1.1's `scan_body` opt-in.
- **`BeaconConfigLoader` was net-new infrastructure, not a one-line addition.** Sized as its own atomic commit per the research recommendation; future SDK config keys reuse this loader.
- **SLF4J 2.0's `slf4j-simple` ships `NOPMDCAdapter`** — `MDC.put` silently no-ops, `MDC.get` always returns null. Caught by `EnricherTest` Day 1. Fix: `logback-classic` as `testRuntimeOnly` on `:beacon-sdk-java`, then again on `:conformance-java` for the same reason (C11(b) reads MDC).
- **Spring `@Async` proof needed `spring-context` on the test classpath.** Added as hard-coded `testImplementation` (no version catalog entry) on both `:beacon-sdk-java` and `:conformance-java` — proper catalog entry lands in M1.7 with the starter.
- **Pre-existing C2 daemon-thread leak surfaced as soon as `BeaconLeakGuard` was registered.** Fixed in the same commit (try/finally + `sdk.close()`) — exactly the side-quest the research flagged.
- **1 MB-key adversarial fixture (RedactorTest) exceeded the 5 ms budget** because `String.toLowerCase(Locale.ROOT)` is O(n) and intrinsic. Fix (folded into the test commit): pre-compute `maxKeyLen` in `Redactor`'s constructor and short-circuit `matches()` on length before lowercasing. Now resolves in microseconds.
- **`BeaconSdk` builder + final `redactor` field interaction.** Initial sketch had the Redactor constructed in the Builder and passed in, but then it couldn't share the SDK's `SdkMetrics` instance (each Builder build creates a fresh `SdkMetrics`). Simplification: pass an optional override down, but always construct the production `Redactor` inside the `BeaconSdk` constructor so it sees the real `metrics` field. Test-injection escape hatch preserved via `Builder.redactor(...)`.
- **`assertThat` overload ambiguity** in `BeaconExecutorsTest`: `executor.submit(...)` accepts both `Runnable` and `Callable`, and a lambda with no body return matches both. Fixed by binding to a `Runnable` local first. Same shape bit `wrap((Runnable) () -> { throw ... })` — explicit cast resolved the overload.

## What could have been done better

- **The C11 sub-cases are inlined into a single `c11_traceContextPropagation` method** with four private helper methods. JUnit 5's `@Nested` would have given clearer test reports per sub-case at the cost of restructuring the harness class — opted against because the M0 freeze covers "class structure," and `@Nested` is structural. Sub-case names are still visible via `assertThat(...).as("C11(a) sync OTel span traceId")`.
- **The conformance test no longer surfaces individual sub-case names in the CI report** for the same reason. Could have used parameterised tests (`@ParameterizedTest` with the four sub-cases as a `Stream<Arguments>`), but the four sub-cases have meaningfully different setups (Spring AppContext for (d) vs none for (a)).
- **`MDC.clear()` between sub-cases is implicit** (the next sub-case constructs a fresh SDK + fresh Spring context). One stray test could pollute the next one's MDC. A test-level `@AfterEach { MDC.clear(); }` would be safer.
- **The Spring `TaskDecorator` example lives only in the conformance test, not in `examples/`.** The plan said `examples/spring-boot-sample/` is deferred to M1.7 (the starter PR). Currently a contributor finds the contract only by reading C11(d). Future improvement: a `docs/usage/async-context.md` snippet linking out.

## Changes carried back to earlier phases

- **`ConformanceTest.c2_emitIsNonBlocking`** (M1.3 code) gained a `try/finally { sdk.close(); }` so `BeaconLeakGuard` no longer trips on the long-standing flusher-daemon leak. Strictly additive — old behaviour was "leak quietly," new is "close cleanly."
- **`ConformanceTest` class** gained `@ExtendWith(BeaconLeakGuard.class)`. Side effect: any future scenario that forgets `sdk.close()` will fail immediately rather than degrading the JVM until later scenarios become flaky.
- **`:conformance-java`'s `build.gradle.kts`** gained `testRuntimeOnly(libs.logback.classic)` + `testImplementation("org.springframework:spring-context:6.1.14")`. The Spring entry is M1.6-only and will be replaced by a version-catalog reference in M1.7 with the Spring Boot starter.

## Journal

- Plan-mode session for plan 04 was tight: a single checkpoint between Task 3 (SDK build green) and Task 4 (conformance harness edits — high blast radius). The checkpoint earned its keep — running `./gradlew :beacon-sdk-java:build` first meant the conformance edits had a known-good SDK to lean on.
- Order matters: built `BeaconExecutors` (Task 1) before wiring `emit` (Task 2) so the SDK pipeline could be exercised end-to-end on the first conformance run.
- The C11(d) Spring `TaskDecorator` setup was the biggest single rabbit-hole. Two false starts: (1) instantiating `C11AsyncEmitter` directly without Spring's AOP proxy → `@Async` was a no-op; (2) trying to inject the per-test `BeaconSdk` via constructor → Spring's bean lifecycle couldn't see the test's local. Settled on a `ThreadLocal<BeaconSdk> CURRENT_SDK` slot on the `@Configuration` so the bean factory reaches the active SDK at refresh-time. Pragmatic; the starter (M1.7) will replace it with a properly-scoped bean.
- First full conformance run after un-disabling: 12/12 green on the first attempt. Felt unreasonable. Diagnosis: the wiring (Tasks 1–3) had been incrementally verified by the SDK unit suite, so the conformance run was just exercising integration — the unit suite had already caught the bugs that would have shown up as conformance failures.
- The `BeaconLeakGuard`'s `Thread.sleep(50)` grace period before the assertion is a small wart — gives in-flight `close()` calls time to join. Without it, fast scenarios race the daemon-thread shutdown. The unit tests didn't need it because they explicitly `awaitTermination`; the conformance test doesn't always.
