# M1.9 — Java CI hardening

## What I did

- **Plan 03.1-01** — landed Spotless (google-java-format). Pinned
  `com.diffplug.spotless 7.0.2` in `gradle/libs.versions.toml` and
  applied it via the root `subprojects { ... }` block; configured
  google-java-format 1.28.0 + `removeUnusedImports` + trailing-WS
  trim + EOF newline; configured the `kotlinGradle` target with
  ktlint 1.3.1. One mechanical reformat baseline commit (`ae79278`,
  50 .java files across 5 subprojects). Wired `spotlessCheck` into
  `.github/workflows/java-sdk.yml` immediately before
  `Build (assemble + test)` so format drift fails fast (`b45df78`).

- **Plan 03.1-02** — landed JaCoCo report-only coverage. Applied

  ADR-0012's deferred-threshold rationale.
- **Plan 03.1-03** — landed Javadoc `-Werror`. Added a

  root `subprojects` configuration, gated on `project.name in

  `{beacon-sdk-java, beacon-spring-boot-starter}`). Options:
  `-Werror`, `-Xdoclint:all`, `-Xdoclint:-missing -quiet`,
  `isFailOnError = true`. New `Javadoc compile gate (-Werror)`

- **Plan 03.1-04** — landed PR-title Conventional-Commits lint.

- **Plan 03.1-06 (this one)** — wrote ADR-0012 (the CI hardening

## Problems I faced

- **JDK 25 launcher broke Spotless 6.x.** First `./gradlew
  spotlessApply` after Plan 01's wiring threw
  `NoSuchMethodError: 'java.util.Queue
  com.sun.tools.javac.util.Log$DeferredDiagnosticHandler.getDiagnostics()'`.
  The internal compiler API signature changed in JDK 22+ from
  `Queue` to `List`; google-java-format only patches up to 1.27.x
  for the old signature. The Gradle launcher on the executor host
  is JDK 25 (mise-managed) even though the project toolchain is
  JDK 17 — Spotless runs in the launcher JVM, not the toolchain
  JVM. Fix: bumped to Spotless 7.0.2 + GJF 1.28.0 (first GJF
  release with JDK 24/25 launcher support; still supports JDK 17
  downward, so CI's Temurin 17 stays green). The plan had pinned
  6.25.0 / 1.22.0; the bump is the only Rule-3 blocking deviation
  across the milestone.

- **`conformance-java`'s `srcDirs(".")` quirk fought Spotless.**
  Two problems stacked: the default `target("src/**/*.java")`
  matched nothing in the harness (CLAUDE.md known gotcha), and
  the default `kotlinGradle` target overlapped with the test
  sourceSet (both reference the project root), tripping Gradle's
  implicit-dependency validator. Fix: per-subproject Spotless
  override (`target("*.java")` + `targetExclude("build/**",
  "bin/**")`) plus an explicit
  `tasks.named("compileTestJava") { mustRunAfter(
  "spotlessJava", "spotlessKotlinGradle") }`. Minimum-surface fix
  that respects the M0 file map.

- **The expected Javadoc warning flush was empty.** Plan 03 had
  budgeted explicit time for a fix-pass against pre-existing
  `{@link}` / `@param` / HTML warnings on the two public-API
  subprojects. The first `-Werror`-enabled run exited 0
  immediately. M1.6 / M1.7 / M1.8 dev discipline kept the doc
  tags clean as code landed; the anticipated PITFALL #23 "one-time
  tail" was a no-op for this milestone. (Future JDK bumps will
  still produce the tail — PITFALL #23 stays on the books.) I
  collapsed Plan 03's Task 1 + Task 2 into a single
  `build(03.1-03):` commit and let the deliberate-regression
  smoke test (inject a broken `{@link}`, confirm `-Werror` fires,
  revert) prove the gate works.

- **Wave-2 parallel siblings raced on `build.gradle.kts`.**
  Plan 02 (JaCoCo) and Plan 03 (Javadoc) both wanted to add
  blocks to the root `subprojects { ... }` configuration at the
  same time. The Javadoc commit (`b1657c2`) landed first and
  `git add`-ed the whole file, bundling JaCoCo's diff with it.
  Semantically equivalent to a Plan 02-owned commit on that
  file, but it means the JaCoCo plumbing's commit message reads
  `build(03.1-03):` rather than `build(03.1-02):`. Carry-forward:
  future phases with multi-plan single-file overlap should
  serialise root-config edits or use `git apply --cached` with
  hand-crafted hunks (the pattern Plan 03 used on
  `java-sdk.yml` to surgically stage only its own change). Plan
  04 (PR-title lint, workflow-only file) and Plan 05 (JMH
  nightly, new workflow file) had no overlap so they landed
  clean.

- **YAML regex quoting trap in Plan 04.** The plan's verbatim
  YAML block had unquoted regex values:
  `headerPattern: ^(\w+)(?:\(([\w\-\.\/]+)\))?(!)?: (.+)$`. The
  embedded `: ` inside the regex is read by YAML as a key/value
  separator and breaks parsing at line 42 col 58. Single-quoting
  the regex strings (single-quoted YAML treats backslashes
  literally — no escaping needed) is the minimum-surface fix.
  Lesson for Plan 06 reconciliation: verbatim YAML snippets in
  plan markdown should be lint-checked
  (`python3 -c "import yaml; yaml.safe_load(...)"`) before being
  copied into workflow files. Adding to the plan-authoring
  checklist for M2.

- **CI-05 count vs roadmap's pre-planning estimate.**
  `.planning/ROADMAP.md` listed Phase 3.1's requirements as
  "CI-01, CI-02, CI-03, CI-04" — the pre-planning estimate. The
  final tracked count is five (JMH nightly = CI-05). Wave-3
  deterministic slot assignment confirmed CI-05 was clean to
  claim once Plans 02/03/04 had filled CI-02..CI-04 in Wave 2.
  This plan's Step 5 reconciles the ROADMAP entry to "CI-01..
  CI-05" with a one-line parenthetical pointing at ADR-0012.

- **`samplingRatio` is still a `BeaconConfig` record component
  with no env/sysprop wiring in `BeaconConfigLoader`** — same
  carry as the M1.8 journal. Not in scope for M1.9; M2 owns it
  as part of Python parity work. Logging the carry here so the
  M1 retrospective stays coherent across milestones.

## What could have been done better

- **The Spotless reformat should arguably have been split
  per-subproject for cleaner `git blame`.** Five commits instead
  of one would make future archaeology on a specific file point
  at the smaller scope. Trade-off: five commits also means five
  CI runs of `spotlessCheck` to verify each, plus more cognitive
  load reviewing the PR. I chose the single-commit path because
  the diff is purely mechanical (`google-java-format` is
  deterministic; the diff against the canonical output is what
  it is). If a future milestone bumps GJF and needs another
  reformat, revisit the per-subproject pattern.

- **The JaCoCo report could be one-per-subproject artifacts
  instead of a single combined one.** A single
  `jacoco-coverage-report` zip is easier to find in the GitHub
  Actions UI but means a reader has to drill into 4 subdirs to
  find the relevant subproject. Per-subproject artifacts would
  surface "which subproject regressed" at the artifact-name
  level. For now (no threshold gate, no per-subproject regression
  detection), the combined shape is fine. Revisit when the
  threshold gate lands.

- **The JMH nightly could have shipped with a stub
  regression-detection script** even though the gate is
  explicitly off. A skeleton script that downloads the previous
  N artifacts, computes the median, and prints a delta-vs-current
  table (without exiting non-zero) would have been ~30 lines of
  Python and would mean the "turn on the gate" PR in a future
  phase is purely a one-line edit. I scoped it out to keep this
  milestone tight; if M2's bandwidth allows, a follow-up PR could
  add the stub.

- **Should ADR-0012 have been written before any of Plans 01–05
  landed?** Conventionally the ADR explains the design and the
  plans implement it. Here the plans landed first and the ADR
  was the reconciliation. Trade-off: writing the ADR first
  would have required predicting all five gates' final shapes
  with their bumps + scoping decisions, which were not all
  known until the plans executed (Spotless 7.0.2 + GJF 1.28.0,
  the empty Javadoc warning tail, the YAML regex quoting trap,
  the 5-subproject scope vs the plan's 4-subproject estimate).
  The ADR-after pattern matches what `CLAUDE.md` §Per-phase
  "done" definition allows — ADR captures the architectural
  call once the decision is firm. I'd defend the choice but
  flag it for the next contributor who lands a multi-plan CI
  phase.

- **The reference to `beacon-sdk-java-spring-boot-starter` in
  Plan 03's body was a plan-text typo (actual subproject is
  `beacon-spring-boot-starter`).** Caught during execution and
  corrected. The lesson is for future planning: when writing
  plans that name subprojects, run
  `cat settings.gradle.kts | rg include` once before quoting
  names. Cheap insurance.

## What's next

**M2 — Python SDK** inherits this CI floor in spirit. Per
`.planning/ROADMAP.md` § CI floor inheritance: M2 ships its
Python CI parity in the SAME PR set as the Python SDK code —
`ruff check` + `ruff format --check` (gated, replaces flake8 /
isort / pyupgrade / pydocstyle-subset), `mypy --strict` (or
`pyright`, decided in ADR-0014) (gated), `pytest --cov`
(report-only, mirroring JaCoCo's measurement-first stance). The
explicit out-of-scope list inherits too: no `darglint`, no
standalone `pydocstyle`, no standalone `black`.

The deferred items from this milestone are now on named carry
ledgers:

- **Coverage threshold gate.** After ~N PRs of artifact data on
  both Java and Python, a single cross-SDK ADR can set a
  defensible floor. Probably Phase 4.1 (M2.1).
- **JMH regression gate.** After ≥7 nightly runs build a
  per-benchmark variance distribution. Threshold methodology
  (e.g. 3σ over rolling-7-night median) is its own ADR
  (anticipated ADR-0013+ — exact number assigned at write time
  by reading `docs/adr/` for the next available slot).
- **Doc publishing (Javadoc Pages + Python docs site).** Phase
  4.1 (M2.1) cross-SDK publishing.

The first observed JMH nightly run on `main` (post-merge) will
backfill actual runtime + per-benchmark variance band into a
future entry — either here or in M2.0's journal, depending on
when the data lands.

## Journal

Five gates in one milestone is a lot of surface, and the
parallel-wave pattern (5 plans, 3 waves) was the right shape
for the work but also the source of every coordination friction
I hit: the `build.gradle.kts` race between Plans 02 and 03, the
`java-sdk.yml` race that Plan 03 surgically resolved with
`git apply --cached`, the CI-05 slot reservation in
REQUIREMENTS.md (Plan 01 had to reserve placeholder rows so
Wave-3 Plan 05 could land deterministically). Single-plan phases
don't have these problems — they also take 5x as long. The
trade-off was worth it.

The two genuinely interesting decisions were both
*deferrals*. JaCoCo + JMH both ship as report-only because
gating without a measured variance band produces false
positives that train reviewers to dismiss the gate. "Measurement
before gating" is the same shape as the milestone-cadence OTel
version review in ADR-0011 and the cross-SDK contract-drift
gate in ADR-0010 — a project pattern is forming where
correctness work lands fast and gating work lands slow, with
each gate having a named precondition (N PRs of data, N nights
of variance, a real user reporting a real bug). Worth naming
explicitly in M2's planning prose.

The Spotless / GJF version bump (6.25.0 → 7.0.2; GJF 1.22.0 →
1.28.0) was the single Rule-3 blocking deviation across the
whole milestone. JDK 25 in the launcher path is a 2026 thing;
the project will see more of these as the GraalVM /
modern-OpenJDK release cadence outpaces the LTS the codebase
targets. CI's Temurin 17 doesn't care — it's only the local
executor host that hits this. Carry note for plan authors:
when pinning a Gradle plugin version, check the plugin's
README for "supported launcher JDKs" and bias toward the
newest stable.

The empty Javadoc warning tail was the most pleasant surprise
of the milestone. PITFALL #23 anticipated a long pain — instead
the gate landed clean. The right reading is not "the pitfall
was wrong" but "the M1.6 / M1.7 / M1.8 dev discipline kept the
doc tags clean as code landed", which is a small but real
testament to the value of code review being human (not just
mechanised) on a small-team project. The pitfall stays on the
books because the JDK 17 → 21 → 25 doclint-rule-set
transitions will produce the same tail in the future.

ADR-0012 was the hardest writing in the milestone — not
technically, but rhetorically. The temptation with a
"CI hardening" ADR is to bury the rationale under a list of
tools. The discipline I tried to hold was: each gate gets its
own paragraph naming the explicit trade-off, each rejected
alternative gets named (Checkstyle, Palantir Java Format,
Codecov, SHA-pinning the actions, etc.), and the out-of-scope
list names the *conditions* under which each deferred item
gets reconsidered (not just "not now"). That's the part that
future maintainers actually need — the list of doors the ADR
deliberately left unlocked.

Final shape: 6 plan-level commits + 2 reconciliation commits
in this plan, all atomic, all Conventional Commits, no AI
attribution. Five tracked requirements; one ADR; one journal
entry. The CI floor is locked in before M2.
