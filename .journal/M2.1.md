# M2.1 — Python bounded buffer + drop policy

## What I did

- **Plan 04.1-01** — built `beacon.pipeline.BoundedBuffer` over
  `queue.Queue(maxsize=N)`: a non-blocking `offer()` that dispatches three drop
  policies via `match` — `DROP_NEWEST` (reject the incoming record, return
  `False` on full), `DROP_OLDEST` (evict the head under a `threading.Lock`,
  accept, increment `dropped` per eviction, always return `True`), and
  `SPILL_FALLBACK` (a fail-loud `NotImplementedError("M2.3: ...")` seam). Added
  `size`/`capacity`/`policy` accessors and `drain_to(sink, max)` /
  `get(timeout_ms)` flusher seams for M2.2. Alongside it: `beacon.config.DropPolicy`
  enum + a minimal frozen `BufferConfig(buffer_capacity=10_000,
  drop_policy=DROP_OLDEST)` carrier (Java `BeaconConfig.defaults()` parity for
  those two slots), and the first three real `beacon.metrics.SdkMetrics`
  counters (`records_enqueued`, `records_dropped`, `buffer_depth`), each guarded
  by a single `threading.Lock`. 13 new unit tests (39 total). Three commits:
  `4b1f69b` / `8e32f9c` / `acfa49c`.
- **Plan 04.1-02** — un-skipped C2 (`test_c2_emit_is_non_blocking`) and C3
  (`test_c3_buffer_overflow_drop_policy`) on the Python conformance harness and
  wired them to the real `BoundedBuffer`. C2 times 1000 `offer()` calls against
  a never-drained buffer and asserts p99 < 1 ms; C3 does capacity 100 + 1000
  offers under DROP_OLDEST and asserts `metrics.dropped >= 850` (the
  `scenarios.yaml` gate; observed exactly 900) + `buf.size == 100`. Followed the
  M2.0 C12 un-skip precedent exactly: only the skip decorators + bodies moved
  (plus a guarded SDK import + a `_rec` helper); the M0-frozen C1–C12 scenario
  list and class structure are unchanged. One commit: `0180a52`. Harness now
  reports 12 passed / 8 skipped.
- **Plan 04.1-03 (this one)** — drafted **ADR-0014** (Python bounded buffer +
  drop policy, the Python idiom of Java ADR-0003), wired its CLAUDE.md index
  one-liner and the `docs/M2-ROADMAP.md` M2.1 cross-link, recorded the new
  `queue.Queue` pitfall (#24), reconciled the PSDK-04 requirement wording,
  added the CHANGELOG `[Unreleased]` M2.1 block and this journal. PR opens for
  human review + rebase-merge.

## Problems I faced

- **`queue.Queue` has no atomic evict-then-put — the central design knot of the
  phase.** Java's `ArrayBlockingQueue.offer` loop is internally atomic per call,
  so the DROP_OLDEST "evict head, then accept new" sequence cannot interleave
  across concurrent producers. `queue.Queue` exposes only the separate
  `get_nowait()` + `put_nowait()` primitives, so two producers *can* interleave:
  A evicts, B evicts, A puts, B puts → two evictions for one logical insert,
  which would over-drop and corrupt the `dropped` counter under load. I guarded
  the DROP_OLDEST evict+put critical section with a single `self._policy_lock`
  (DROP_NEWEST is a lone `put_nowait` and needs no lock), with an
  `except queue.Empty: pass` inside the evict loop as the Python mirror of
  Java's `if (poll() != null)` consumer-race guard. This is the new **Pitfall
  #24** and the load-bearing decision in ADR-0014.
- **`SdkMetrics` thread-safety — Python has no `AtomicLong`.** Java backs each
  counter with an `AtomicLong`; Python doesn't have one. `itertools.count` was
  the tempting lock-free option but is wrong here: you can't read its current
  value without consuming it, and concurrent `next()` plus a separate read loses
  updates — fatal for `buffer_depth`, which is a *gauge you read*. I went with
  plain `int`s under a single `threading.Lock`, and proved it with an 8×1000
  concurrent-increment test (no lost updates). Cheap at these mutation rates;
  documented the escape hatch (lock-free `deque` + separate counter) in ADR-0014
  if a future profile shows contention.
- **Modeling a "stalled exporter" with no real flusher yet.** C2/C3 want to
  exercise the buffer under back-pressure, but the flusher (M2.2) and handler
  (M2.6) don't exist at M2.1, so there's no full `emit()` path to drive. I
  modeled the worst-case stalled/blocking exporter by simply *never draining*
  the buffer and driving `BoundedBuffer.offer` directly — no consumer is the
  strongest back-pressure, keeping the buffer full for the bulk of the run. It's
  the correct minimal proof at this phase and matches the Java harness intent;
  documented in both test docstrings as a candidate to re-express end-to-end
  once the M2.2 flusher exists.
- **PSDK-04's wording was wrong for the architecture.** The requirement read
  "non-blocking emit uses `logging.QueueHandler` + `QueueListener` with
  `queue.Queue`." But `QueueHandler` offers no per-policy drop semantics — it
  can't satisfy the configurable `DROP_OLDEST | DROP_NEWEST | SPILL_FALLBACK`
  requirement. The non-blocking buffer is the custom `BoundedBuffer`; the
  `QueueHandler`/`QueueListener` `logging`-framework integration genuinely
  belongs to the `BeaconLoggingHandler` (PSDK-06 / M2.6). Reconciled the wording
  and moved the clause.

## What could have been done better

- **The "#20" label drift should have been caught at roadmap time.** The
  M2-ROADMAP / phase-plan prose called this pitfall "#20", but #20 was already
  *Gradle / dependency CVE drift on M3+*. The actual free slot is #24. It's a
  harmless bookkeeping slip, but it means any reader following the roadmap's
  "#20" reference lands on the wrong pitfall. Fixed with an explicit
  numbering note in PITFALLS.md, but a pre-flight "is this slot free?" check in
  the planning step would have avoided it.
- **PSDK-04's mismatch sat latent since requirements were first written.** The
  `QueueHandler` wording was an early-planning guess that didn't survive contact
  with the drop-policy requirement. A "does this satisfy *all* of the
  requirement's sub-clauses?" pass when the M2 phase plan was drafted would have
  surfaced it before M2.1 execution rather than at phase-close.
- **The stalled-exporter model is a direct-offer stand-in, not the real path.**
  It's correct for proving the buffer's non-blocking + drop-policy properties in
  isolation, but C2/C3 won't exercise the *full* emit→buffer→flusher chain until
  M2.2 lands a consumer. Worth a deliberate re-visit there so the conformance
  gates reflect the production path, not just the buffer unit.

## Journal

- *04.1-01* — wrote the buffer first, the policies second, the metrics third.
  The `queue.Queue` non-atomic evict-then-put gap surfaced immediately when I
  reasoned through two concurrent DROP_OLDEST producers — the lock went on the
  *only* the evict+put critical section, not the whole `offer`, so DROP_NEWEST
  pays nothing. Rejected `itertools.count` for `SdkMetrics` after realizing the
  gauge read pattern needs a value you can read without consuming. Measured the
  offer latency in a tight loop (capacity=100, full for ~900/1000 calls): median
  ~4.0 µs, p99 ~5.3 µs, max ~11.3 µs — three orders of magnitude under the 1 ms
  budget, which gave me confidence the C2 gate would pass with huge headroom.
  `LogRecord.minimal(...)` from M2.0 was directly usable as the test-helper
  constructor — no manual 12-field build.
- *04.1-02* — the un-skip was almost mechanical thanks to the M2.0 C12
  precedent: move the skip decorator + body, add a guarded SDK import and a
  `_rec` helper, leave C1–C12 names and structure frozen. The only design call
  was the stalled-exporter model: never drain. C2 standalone p99 ~28 µs
  (vs ~5.3 µs in-process — interpreter/harness overhead, not a regression);
  both orders of magnitude under 1 ms. C3 dropped exactly 900
  (`1000 - capacity 100`), buffer saturated at 100. Harness: 12 passed / 8
  skipped, drift `--sdk all` exit 0.
- *04.1-03* — docs close-out. ADR-0014 mirrors ADR-0003's five-decision shape
  but spends its words on *where Python must diverge*: `queue.Queue` vs
  `ArrayBlockingQueue`, the external lock, plain-int-under-lock vs `AtomicLong`,
  `NotImplementedError` vs `UnsupportedOperationException`. Caught the "#20" vs
  #24 label drift while placing the pitfall — #20 was already taken by Gradle
  CVE drift. PSDK-04's `QueueHandler` wording was the other reconciliation: it
  belongs to the M2.6 logging bridge, not the M2.1 buffer. Confirmed the
  CLAUDE.md ADR index still jumps 0006→0009 on this branch (0007/0008 live on
  the reconciliation branch) and deliberately added only ADR-0014. The PR opens
  here for human review and rebase-merge; the `.planning/` tracker edits
  (PITFALLS #24, PSDK-04) are local-only — `.planning/` is gitignored — so they
  ship as working-tree state, not in the PR, matching the repo's established
