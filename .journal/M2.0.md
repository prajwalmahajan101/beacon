## Problems I faced

- **Byte-for-byte parity was claimed without a live Java run — since closed.** The
  canonical-JSON regression literal locked in
  `test_byte_for_byte_against_java_known_fixture` was originally *computed by the
  executor* from `spec/01` §1 + the `format_rfc3339_nano` contract — it was **not**
  diffed against a live `CanonicalJson` run during the Python-only plans. **Resolved
  post-merge (2026-06-29):** the real `io.beacon.sdk.record.CanonicalJson.serialize`
  was compiled (JDK 25) and run on the exact equivalent record
  (`Instant.ofEpochSecond(1_700_000_000L, 123_456_789L)`, sev 9, `INFO`, `hello`,
  `LinkedHashMap{service.name=svc, telemetry.sdk.language=python}`); its output is
  **byte-identical** to the Python literal for this `ns % 1000 != 0` fixture
  (`EQUAL : true`). The check ran against a throwaway classpath and was not committed
  — a permanent cross-SDK golden corpus stays M2.6 scope (see carry below).
- **The 9-digits-always vs Java-trims divergence.** `format_rfc3339_nano` always
  pads to 9 fractional digits; Java's `CanonicalJson` renders
  `Instant.toString()`, which trims trailing zeros to 0/3/6/9 digits. They are
  byte-identical only for sub-microsecond timestamps with a non-zero ns
  remainder. For ms-aligned or whole-second records the two SDKs produce
  *different bytes* (`...123000000Z` vs `...123Z`). The M0 schema's `timestamp`
  pattern permits any fractional width, so neither is "wrong" against the
  contract — but a shared golden-record corpus would trip on this. I chose
  always-9 deliberately as the strongest defense against the ns-truncation trap;
  the reconciliation is deferred.
- **Two in-plan-text bugs surfaced during execution (both Rule-1 auto-fixes).**
  (a) 04-02's plan asserted `format_rfc3339_nano(1234567890123)` ends in
  `.000000123Z`, but `1234567890123 % 1_000_000_000 = 567890123` → that's
  `.567890123Z`. The input was wrong, not the formatter; corrected to
  `1_234_000_000_123`. (b) 04-03's plan specified `config/_keys.py` as a
  *pure dynamic* YAML load, while the same plan's drift gate asserts every
  `BEACON_*` env literal appears *in source*. A dynamic-only loader spells out
  zero literals, so the drift gate's own positive smoke test reported all 15
  env literals missing — the two requirements were in direct tension. Fixed by
  adding in-source anchor tuples pinned set-equal to the YAML at import (the
  exact Java `BeaconConfigLoader` + `ConfigKeysContractTest` pattern).
- **The fs-walk loader is more defensive than the research prescribed.** RESEARCH
  suggested a fixed 4-entry CWD list; in practice the harness can run from the
  SDK rootdir, the repo root, or the venv, so the loader walks CWD 0..4 levels
  *and* `__file__` parents. More robust, but it's the kind of "works on my
  machine ladder" that deserves a real `importlib.resources` answer eventually.

## What could have been done better

- **The single-PR coupling is fragile.** All four 04-0x plans *must* land in one
  PR, because 04-01 creates `beacon-sdk-python/` (which trips the drift stub red)
  and only 04-03 lands the introspection that turns it green again. Between those
  two commits `main` would be red. We knew this going in (RESEARCH Open Questions
  #2) and managed it by landing the stack atomically — but a cleaner sequencing
  would have put the drift-introspection commit *first* (or gated the stub on a
  feature flag) so each commit left `main` green and the plans could merge
  independently. Worth fixing before M2.1 if we ever want per-plan PRs.
- **`config/_keys.py` is thinner than M2.1 will want.** It exposes env-var /
  sysprop *spellings* and a surface count, but not the full canonical-surface
  tree with types/defaults. M2.1's `BeaconConfig` loader (env > sysprop >
  builder precedence, mirroring Java `BeaconConfigLoader`) will have to grow this
  into a real structured config object. Stubbing only the literals now was the
  right scope call for M2.0, but the next phase inherits the growth work.
- **No Java cross-check task in the plan.** Given the byte-parity claim is the
  single most load-bearing correctness property of this phase, the plan should
  have included an explicit "run Java `CanonicalJson.serialize` on the equivalent
  `Instant` and diff" task. It didn't, so the parity literal ships unverified.

## Changes carried back to earlier phases

- **No M0 / M1 source touched.** Both files under
  `beacon-s0-contract/conformance/` that this phase edited
  (`test_conformance.py` un-skip of C12, `check_contract_drift.py` Python
  introspection) are *harness/tooling* changes, not contract changes — the
  M0-frozen scenario list C1–C12 and the schema/spec are unchanged. The C12
  un-skip follows the documented Java precedent (un-disable C-scenarios per
  phase) and needs no ADR amendment.
- **ADR-0011 §4 carve-out closed.** ADR-0011 (M1.8) explicitly punted the Python
  OTel pin "until the Python SDK lands." ADR-0013 is the sibling it promised —
  this phase closes that open thread.
- **CLAUDE.md ADR index** gains the ADR-0013 one-liner (12 → 13 entries),
  recorded in this plan's Task 3.
- **Carry to M2.6:** if strict byte-parity with Java is ever required for a
  shared golden corpus, either trim Python's trailing fractional zeros to match
  Java or widen Java to always-9 (I'd recommend the latter — always-9 is the more
  defensible wire contract). A reference fixture generated from a live Java run
  should be checked into `beacon-s0-contract/conformance/python/fixtures/` at
  that point.
