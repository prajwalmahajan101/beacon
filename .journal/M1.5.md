## What I did

- Made `BatchFlusher.drainAndStop(timeoutMs)` the drain primitive. Lifecycle stays in one class: `start() / stop() (non-draining) / drainAndStop(timeoutMs)`.
- `BeaconSdk.close()` is a thin wrapper that calls `drainAndStop(config.shutdownDrainTimeoutMs())`.
- Drain covers both the flusher's in-flight batch (via runLoop exit hook) AND the buffer remainder.
- Drain reuses the configured sink path — `ResilientSink`'s retry+fallback applies for free.
- `close()` is idempotent via `AtomicBoolean closed.compareAndSet(false, true)`.
- JVM shutdown hook deferred to M1.7 (sits naturally next to the Spring Boot lifecycle wiring).

## Problems I faced

- **First sketch had `BeaconSdk.close()` doing the drain itself** — stop the flusher, then loop `buffer.drainTo` + `sink.accept` from the calling thread. Worked but split lifecycle state between `BeaconSdk` and `BatchFlusher`. Pulled the drain into `BatchFlusher.drainAndStop` and made `close()` a one-liner.
- **First version of the runLoop exit hook only flushed the in-flight batch on natural stop**, not on `InterruptedException`. Test caught it: interrupting the flusher mid-batch lost records. Fixed by moving `if (!batch.isEmpty()) flush(batch)` outside the `try/catch` so it runs regardless of how the loop exits.
- **C3 stalled sink would deadlock under new close semantics.** It used a single `wait/notify` cycle per `accept()` call; the M1.5 drain handed it the buffer remainder which `wait()`'d again with no notifier. Fix: loop on `AtomicBoolean released` so a single `notifyAll` permanently unblocks. Caught by `:conformance-java:test` during pre-merge run.

## What could have been done better

- **`BeaconSdkEmitTest` has now been touched in three milestones** (M1.2 wrote it; M1.3 added `sdk.close()`; M1.5 changed it to `sdk.flusher().stop()`). Each revision was small but the cumulative churn signals the test cases are doing double-duty (testing buffer + emit + SDK lifecycle). Should be split into focused buffer-level tests and SDK-level tests in a future tidy-up.
- **`drainAndStop` returns void.** No indication to the caller whether the drain completed within budget or got cut by the join timeout. A `boolean` return ("fully drained") would let callers decide whether to log a warning. Easy v2 improvement.
- **The 5 s drain budget is wildly generous** for an in-process drain — the C9 test completes in milliseconds. Could have used a tighter assertion (e.g. `<= 500ms`) to catch regressions earlier, at the cost of CI flake on slow runners.

## Changes carried back to earlier phases

- `BatchFlusher.runLoop` (M1.3 code) gained an exit hook to flush the in-flight batch (commit 2). Strictly additive — old behaviour was "drop the in-flight batch on stop," new is "flush it first."
- `BeaconSdkEmitTest` (M1.2/M1.3 test) switched from `sdk.close()` to `sdk.flusher().stop()` (commit 3). Same intent, non-draining variant.
- C3 `StalledSink` (M1.4 code) rewritten to loop on `AtomicBoolean released` instead of a single `wait/notify` (commit 3). Same observable behaviour pre-M1.5; necessary for the close-now-drains path.
