## What I did

- Made resilience a `BatchSink` decorator (`ResilientSink`), not exporter-internal logic. `OtlpExporter` fails fast; `ResilientSink` drives retry + fallback.
- Picked AWS "full jitter" backoff — uniform random in `[0, min(baseMs * 2^attempt, maxMs)]`. Overflow-safe shift.
- Converted `FallbackSink` from a single class with a `Target` enum (M1.0 stub) into an interface with `StderrFallbackSink` + `FileFallbackSink` impls + `fromConfig` factory.
- Delegated record conversion to OTel's `SdkLoggerProvider` (`Logger.logRecordBuilder().setTimestamp(...).setSeverity(...).setBody(...).setAllAttributes(...).emit()`) instead of hand-rolling `LogRecordData` boilerplate.
- Wired the M1.4 SdkMetrics counters (`exported`, `exportFailures`, `fallbackWrites`) — replaced the M1.4-pending stubs that threw.
- Production wiring stays explicit: `BeaconSdk.builder().sink(ResilientSink.of(otlp, config, metrics))`. No builder auto-wrap.

## Problems I faced

- **First draft of C6/C7/C8 tests had a metric-routing bug.** Built a throwaway SDK to grab `metrics()`, then closed it and built a "live" SDK with the resilient sink. But the resilient sink and the live SDK had **different `SdkMetrics` instances** — assertions on `live.metrics().fallbackWrites()` always returned 0 because the fallback was incrementing a different counter. Fix: test-owned `SdkMetrics` passed to both `ResilientSink` and the `CapturingFallback`, exposed via a `Wired` record. Caught only because the conformance assertions were precise enough to surface the mismatch.
- **C3 broke when the stalled-sink swap landed.** The M1.3 fix (`sdk.close()` to stop the flusher) was replaced with a real `StalledSink` that blocks inside `accept()`. But the default `batchMaxRecords=512` meant the flusher pre-drained ~500 records into its in-flight batch before the sink blocked — buffer only saw ~500 records, drops = 388 instead of ≥ 850. Fix: `.withBatchMaxRecords(1)` in the C3 SDK config so the flusher steals exactly one record before stalling.
- **OTel's `Logger.logRecordBuilder()` has no direct severity-number setter** — only `setSeverity(Severity)`. Had to map Beacon's severity number → OTel's `Severity` enum using the same band table from spec/01 §1.1 that `SeverityMapper` already encodes. Added `OtlpExporter.severityFromNumber` as the OTel-facing reflection.
- **`provider.forceFlush().join(5s)` was the only way to make `accept(batch)` synchronous.** Without it, OTel's `BatchLogRecordProcessor` returns immediately and the test sink sees nothing. Used `SimpleLogRecordProcessor` to bypass — one network call per record, but Beacon's flusher already batched so that's fine.

## What could have been done better

- **Should have caught the metric-routing bug at design time, not test time.** The `Wired` helper makes the test legible, but the underlying issue — `SdkMetrics` being created per-SDK with no injection path — is a design gap. A builder option to inject metrics would have made the tests trivial and is the right v2 fix.
- **Spent too long debating whether to include real OTLP transport in M1.4** before realising that C6/C7/C8 don't actually exercise it (they use test sinks). The plan-mode AskUserQuestion was the right call but I should have framed it more precisely.
- **The `OtlpExporter` smoke test only verifies construction**, not a real round-trip. Real verification is M1.7's job (Spring Boot starter + live collector) but documenting that explicitly in the test would have been worth 60 seconds.

## Changes carried back to earlier phases

- `SdkMetrics.incExported(int)` / `incFallbackWrite(int)` take batch sizes (commit 2). M1.2/M1.3 counters were single-increment; M1.4's are bulk-add. Old getters unchanged.
- `FallbackSink` shape changed from class-with-enum (M1.0 stub) to interface-with-impls. The stub had no callers, so no migration needed.
- C3 test rewritten (commit 7) to use a real `StalledSink` instead of M1.3's `sdk.close()` workaround. Matches `scenarios.yaml`'s `exporter: stalled` verbatim now.
