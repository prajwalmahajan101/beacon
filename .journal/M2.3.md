## Problems I faced

- **The criterion-#4 contract tension (the load-bearing decision).** The M2-roadmap success criterion #4 asked for a fallback path defaulting to `${BEACON_FALLBACK_DIR}/beacon-fallback.log` with size-cap rotation. But `beacon-s0-contract/conformance/config-keys.yaml` — an ADR-0010 cross-SDK source-of-truth mirrored by Java — defines **only** `fallback-sink` (default `stderr`, spec `stderr | file:<path>`): no `fallback-dir`, no rotation key, and the Java `FileFallbackSink` does not rotate. Adding `BEACON_FALLBACK_DIR` or a rotation-cap key would be a cross-SDK CONTRACT CHANGE that diverges the Python config surface from Java and desyncs the ADR-0010 drift gate's parity intent. Resolved by **honoring `fallback-sink`** — stderr default, `file:<path>` opt-in, NO new `BEACON_*` keys (drift gate stays exit 0, Java parity intact, C6/C7/C8 green) — and **deferring** `BEACON_FALLBACK_DIR` + rotation to a future ADR-gated additive carve-out (or an internal file-sink behavior, not a new contract surface). Locked in ADR-0016 §5. This was a planner-level contract-tension resolution consistent with the locked OTel pin + Java parity, so it did not need a human checkpoint — but it is the single most important call of the phase and is recorded three places (ADR, CHANGELOG, the planning ROADMAP's struck-through criterion #4).
- **Retry-After-429 scoping.** Criterion #2 wanted 429 handling (an addition over Java, which has none). The hint plumbing exists end-to-end and is unit-tested (`OtlpExportError.retry_after_ms`, `parse_retry_after`, `ResilientSink` flooring the wait with `max(delay, hint)`), but wiring it to a real OTel-Python HTTP 429 response is deferred: `SimpleLogRecordProcessor.force_flush()` returns only a `bool` and hides the HTTP status, so surfacing a `Retry-After` header would need a custom session/response hook — a fragile dependency on OTel HTTP internals that risked C6/C7/C8 determinism. Plumbed the hint, flagged the wiring as post-v1.
- **Keeping C6/C7/C8 deterministic without a live collector.** The scenarios describe a broker going down/up, but the unit under test is `ResilientSink`, not a network. Modeled each with a fake delegate + `base_ms=max_ms=1` (so retries sleep ≤1 ms). C7's 50 records became 50 single-record `rs.accept([...])` batches (no full `emit()` pipeline yet — the flusher assembly is M2.4/M2.6). C8's recovery is driven by a **test-flipped `delegate.up` flag**, not wall-clock `down_ms` — the contract point is "resumes without restart," and the key proof is the *same* `rs` instance exporting after the delegate recovered (no new sink constructed), with `fallback_writes` unchanged post-recovery.
- **The sync-retry stall realization → Pitfall #25.** Writing ADR-0016 §3 made the worst case concrete: `max_retries × backoff_max_ms` = `5 × 5000` ≈ 25 s of `time.sleep` on the `beacon-batch-flusher` daemon thread during a retry storm, blocking the flush loop. The M2.1 bounded-buffer drop policy is the back-pressure escape valve (the host app never blocks; export throughput degrades, not the caller). Captured as Pitfall #25; async retry deferred post-v1. This mirrors the identical Java tradeoff in ADR-0005 §7.
- **Confirming the installed OTel 1.43.0 import paths.** Verified in the frozen venv rather than trusting the plan snippet: the gRPC/HTTP `_log_exporter.OTLPLogExporter` symbols share a name (aliased to distinct symbols), `sdk._logs.LoggerProvider`, `sdk._logs.export.SimpleLogRecordProcessor`, `_logs.SeverityNumber`; `emit` keyword set + `force_flush → bool` + `SeverityNumber(9) == INFO` all confirmed — no API deviation.
- **One test-bug deviation in Plan 02 (Rule 1).** `test_retry_then_success` asserted `len(slept) == 2`, but `RetryPolicy(base_ms=1, max_ms=1)` yields `randint(0,1)` which can be `0`, and `ResilientSink`'s correct `if delay_ms > 0: time.sleep(...)` guard skips that syscall — relaxed to `<= 2` (retry count proven by `d.calls == 3`); no production change.

## What could have been done better

- **Whether the 429 wiring should have been attempted at all.** Plumbing a hint that nothing feeds is honest scoping, but it does leave a half-connected feature in the tree; an alternative would have been to leave `retry_after_ms` out entirely until the wiring landed, keeping the surface smaller. On balance the plumbing is cheap, tested, and documented, and it makes the future wiring a one-hook change — but it is worth flagging that "plumbed but not wired" is a shape a future reader could mistake for "done."
- **A `down_then_up` wall-clock model would have been closer to `scenarios.yaml`.** C8 uses a test-flipped flag instead of honoring `down_ms=1000`. That is deliberate (the contract point is resume-without-restart, and a wall-clock sleep would make the test slow + flaky), but it does mean the harness proves the *invariant* rather than the literal timing the scenario describes. Fine for a unit-level gate; a future integration test against a real collector is where the timing belongs.
- **The `CapturingFallback` / `StderrFallbackSink` ctor takes `metrics`** where the plan snippets showed a no-arg form — anticipated in the plan text, but a reminder that inline verify snippets in a plan are illustrative, not authoritative; the real Wave-1 signatures win.
