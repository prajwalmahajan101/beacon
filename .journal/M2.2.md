## Problems I faced

- **`queue.Queue.get(timeout)` is NOT interruptible by `threading.Event.set()` —
  the central design knot of the phase.** Java ADR-0004 wakes the parked flusher
  via `Thread.interrupt()` on `stop()`; Python has no `Thread.interrupt`
  equivalent. A single long blocking `buffer.get(flush_interval_ms)` would mean a
  `stop()` issued while the loop is idle on a large interval (e.g. C4's
  `flush_interval_ms=60000`, where the loop goes idle right after a SIZE flush)
  could not wake until the full interval elapsed — `stop()`'s `join(1.0)` would
  time out and the thread would leak. The fix is the **chunked poll**: cap each
  `buffer.get()` at `min(remaining_ms, _POLL_CHUNK_MS=50)` and recheck
  `self._stop.is_set()` between chunks in BOTH the idle branch (waiting for the
  first record) and the non-empty branch (waiting out the remaining interval),
  accumulating `monotonic_ns` elapsed so the INTERVAL trigger still fires at
  exactly `flush_interval_ms`. Observed: `stop()` returns in 0.3 ms at
  `flush_interval_ms=60000` (budget 1.0 s); interval fired at 200.6 ms for a
  200 ms config. This is the load-bearing decision in ADR-0015 §2 — the same
  `queue.Queue` primitive that bit M2.1 (Pitfall #24) bites again, on a different
  axis (non-interruptibility rather than non-atomic evict-then-put).
- **Choosing `threading.Event` over a poison-pill sentinel for M2.2.** The
  roadmap mentions a "sentinel posted by `lifecycle.shutdown`" — a poison pill
  posted to the buffer that the loop recognises and exits on. For M2.2 I went
  with a plain `threading.Event` because the chunked poll already gives a bounded
  wake without needing the buffer to carry a control message; the sentinel is
  M2.4 wiring (it can `set()` the Event AND post a wake sentinel). Documented the
  split in ADR-0015 §6 so M2.4 knows the Event is the M2.2 primitive and the
  sentinel is additive.
- **Making C5's 200 ms interval test non-flaky.** A tight `assert elapsed ≈ 200ms`
  would flake under CI scheduling jitter. I used a `_wait_until(predicate,
  timeout=2.0)` poll-until-condition with a generous bound and recorded the
  observed latency in the audit trail rather than asserting it tightly — the
  contract point is that the interval trigger fires at all without a size cap,
  not its precise latency. C4+C5 ran 3× back-to-back clean.
- **The `drain_and_stop` M2.4-seam decision.** I preferred a fail-loud
  `NotImplementedError("M2.4: graceful drain")` over implementing a half-form
  drain now — the buffer-drain-then-flush-tail plus `atexit`/SIGTERM wiring is
  M2.4's C9 scope. Mirrors the M2.1 `SPILL_FALLBACK` fail-loud precedent.
- **The `flush_max_size` → `batch_max_records` canonical-name reconciliation.**
  The roadmap informally calls the size knob `flush_max_size`; the canonical
  cross-SDK contract name (config-keys.yaml C4 + the existing
  `BEACON_BATCH_MAX_RECORDS` anchor) is `batch_max_records`. `FlusherConfig` uses
  the canonical spelling for cross-SDK parity, with a docstring line recording
  the mapping. Picking the canonical name meant zero `config/_keys.py` change and
  a green drift gate.

## What could have been done better

- **The PSDK-05 mis-mapping should have been caught at roadmap time.** The
  M2-ROADMAP listed `Requirements: PSDK-05` for Phase 4.2, but PSDK-05 is the
  *severity-mapping* requirement — an M2.0 deliverable that shipped with C12 and
  was wrongly left Pending. The batch flusher has no standalone PSDK requirement
  at all; its acceptance is C4 + C5 under the PSDK-08 umbrella. This is the same
  class of slip as M2.1's PSDK-04 `QueueHandler` wording and the "#20"→#24 label
  drift — a pre-flight "does this requirement actually name this phase's
  deliverable?" check in planning would have surfaced it before phase-close.
- **The conformance C4/C5 tests can't reuse the autouse leak guard.** pytest
  scopes a `conftest.py` to its own subtree, so the unit-suite leak guard at
  `beacon-sdk-python/tests/conftest.py` does not cover
  `beacon-s0-contract/conformance/python/`. I used a `try/finally flusher.stop()`
  per body instead of adding a conftest under the M0-frozen tree (which would
  raise freeze-scope questions) — correct, but it means the leak invariant is
  enforced two different ways in two directories. A shared helper invoked from
  both would be cleaner if the frozen-tree constraint ever relaxes.
- **C2/C3 still don't exercise the full emit→buffer→flusher chain.** M2.1's note
  flagged re-expressing C2/C3 end-to-end once a real consumer (the flusher)
  existed. M2.2 now has that consumer, but I scoped this phase to C4/C5 only and
  left the C2/C3 end-to-end re-expression as a deliberate non-goal. Worth
  revisiting when the M2.6 handler lands the true emit path.

## Journal

- *04.2-01* — wrote the two leaf deps first so the flusher loop had something to
  call. The canonical-name call (`batch_max_records` vs the roadmap's
  `flush_max_size`) was the only real decision; picking the contract name kept
  the drift gate green with zero `_keys.py` edits. The 8×1000 concurrent-increment
  test reused the M2.1 threading style verbatim — both counters hit 8000, no lost
  updates.
- *04.2-02* — the chunked poll surfaced the moment I reasoned through `stop()` on
  a 60 s interval: a single `buffer.get(60000)` parks the thread for a minute and
  `join(1.0)` times out. I almost reached for a poison-pill sentinel before
  realising a small constant chunk + a stop-flag recheck is the simpler answer
  (and it makes the INTERVAL clock exact via accumulated elapsed). Measured
  `stop()` at 0.3 ms on the 60 s interval — that's the regression guard that
  would fail if the chunked poll ever regressed to a single long blocking get.
  `BatchSink` as a `runtime_checkable Protocol` over a bare `Callable` was a
  parity-with-Java call: the named interface documents the `accept` contract and
  the M2.3 exporter structurally satisfies it. The leak-guard fixture is
  poll-until-gone, not a fixed sleep — `stop()`'s bounded join already guarantees
  the thread is gone, the poll just absorbs a benign mid-exit race.
- *04.2-03* — the un-skip was nearly mechanical thanks to the M2.0 C12 / M2.1
  C2+C3 precedent. The one design call was trigger isolation: C4 sets a 60 s
  interval so only SIZE can fire; C5 sets a 10000 size cap so only INTERVAL can
  fire — so any observed flush is unambiguously attributable to the trigger under
  test. No conftest under the frozen tree; `try/finally flusher.stop()` per body
  is the leak safeguard there. Observed C5 flush at 202.4 ms for a 200 ms config,
  well inside the 2 s test bound; C4+C5 non-flaky across 3× repeats.
- *04.2-04* — docs close-out. ADR-0015 mirrors ADR-0004's decision shape but
  spends its words on where Python must diverge: the chunked poll (vs Java's
  interrupt), `time.monotonic_ns` (not `time.time`), the `Protocol` sink (not a
  bare callable), and the `drain_and_stop` M2.4 seam. The PSDK-05 mis-mapping was
  the headline reconciliation — PSDK-05 is severity mapping (M2.0, C12), not the
  flusher, and was wrongly left Pending; fixed at both the checklist and the
  status table, with the flusher's real coverage (C4+C5) mapped under PSDK-08.
  Annotated Pitfall #19 rather than adding a new number — the chunked-poll insight
  lives in ADR-0015 §2 and the `queue.Queue` hazard is already Pitfall #24. The PR
  opens here for human review and rebase-merge; the `.planning/` tracker edits
  (PITFALLS #19 note, PSDK-05/08) are local-only — `.planning/` is gitignored — so
  they ship as working-tree state, not in the PR, matching the M2.1 pattern.
